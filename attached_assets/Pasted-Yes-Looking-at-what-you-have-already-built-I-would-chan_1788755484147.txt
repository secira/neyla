1. Sign up.
2. Create a project.
3. Describe an application.
4. Have Neyla generate it.
5. Modify it through conversation.
6. Preview it.
7. Connect GitHub.
8. Push the source code.
9. Run Neyla Check.
10. Publish the application.
11. Receive a public URL.
12. Open the application successfully.
13. Return later and continue editing.
14. Recover the project after clearing browser storage.
15. Invite a teammate and collaborate.

The most important metric is:

> Percentage of newly created projects that successfully reach a live deployment.

## DEVELOPMENT PROCESS

Do not implement all requirements in one operation.

Work in milestones.

For each milestone:

1. Inspect existing implementation.
2. Identify reusable code.
3. Identify affected modules.
4. Explain the implementation plan.
5. Make the smallest safe change.
6. Run tests.
7. Run build.
8. Verify manually where appropriate.
9. Fix regressions.
10. Commit changes.
11. Document what changed.

Do not rewrite working components without justification.

Do not introduce unnecessary dependencies.

Do not migrate architecture and add unrelated features simultaneously.

## And I would make one strategic change to your roadmap

Your original four-layer model was:

**Create → Preview → Own → Deploy**

I would keep it.

But internally I'd now define Neyla as:

# **Create → Understand → Build → Own → Deploy**

Where **Understand** is your emerging moat.

Because the future difference between Neyla and a generic AI coding tool isn't necessarily the quality of the initial generation.

It is:

> **Can Neyla understand an application it created three months ago and safely change it without breaking everything?**

That leads naturally to:

**Project Context → Project Memory → Build Plans → Change Impact → Automated Testing → Deployment**

And *that* is something your current architecture is already positioned to build.

For the next 90 days, I would therefore resist the temptation to expand Neyla's surface area. **Make one thing exceptionally good: a startup founder can arrive with an idea on Monday and have a real, GitHub-owned, production application running by the end of the day.**

Once you achieve that reliably, **then Neyla.dev/MCP becomes a natural second product rather than another unfinished subsystem.**
